Two things worth flagging

⚡ KOLs drive two channels at once

The same kols field powers (a) web_search per-handle rows and (b) last30days xRelated. One card, two retrieval paths.

👤 X enabled but no KOLs

X is still searched — but only the generic brand / category site:x.com row. No handle-level monitoring. The brand's own timeline isn't pulled unless a handle is in the watchlist (and xHandle for last30days is currently null in clients.js:344).

How it actually works · mechanics

freshnessDays the recency dial — what "time window" really means

One number (1–30, default 7) that says how far back to care. It is not a single hard date filter — it does two different things depending on the channel:

SOFT · the X web_search row
The number is written into the search prompt as text: "Prioritize content from the last N day(s). Today: 2026-06-24". web_search has no date parameter — this is just an instruction. A highly relevant older tweet can still surface; recent ones are merely preferred, not enforced.
HARD · the supplementary channels
For last30days and GDELT news the number becomes a real cutoff passed to the fetcher (--lookback-days). Anything older than the window is simply not returned.

Where the one number lands:

  • SOFTX web_search row — prompt bias "prefer last N days" · today's date injected so the model knows what "recent" means. xscout.js:511
  • HARDlast30days X channel — lookbackDays = max(7, freshnessDays), so the floor is 7 days even if you set 1. config-loader.js:467
  • HARDGDELT brand-news — clamped to 1–7 days. runtime.js:229 · news-monitor.js:43

Lower = tighter, today-ish (crittersQuest = 1). Higher = wider net (notTheRug = 7). Clamped to [1,30] at save · config-loader.js:345.

site:x.com the X row is a Google-indexed search — not the X API

The site:x.com OR site:twitter.com row runs through Claude web_search. It finds publicly indexed tweet permalinks — it does not call the X/Twitter API and does not log in. So coverage = whatever the search index has crawled. Login-walled, deleted, or very-fresh (last-few-minutes) tweets may simply not appear. No credentials are used for reading.

PLATFORM_SITE_QUERIES.x · config-loader.js:140 — "x tweet permalinks are indexed by Google; x.com is canonical."

two channels X data arrives via two independent paths

1 · web_search rows — the site:x.com row plus per-handle watchlist rows. Credential-free, index-dependent, soft recency.

2 · last30days service — a separate CLI fetch (hard lookback, floored at 7 days) that can reach X through the watchlist handles passed as xRelated. Runs only when 'x' is enabled and the service is configured.

They merge in the brief; the same KOL handle can feed both at once.

subject what the X row actually queries

The X site row does not search your raw keyword list. It searches subject = companyName + first words of the brand's idea / category (config-loader.js:151–162). Search Parameters (brandKeywords + categoryTerms) is what refines that subject. So editing keywords changes the words after site:x.com OR site:twitter.com — nothing else about the row.

kolSearchMode per-handle vs combined

per-handle (default) = one search row per @handle → each handle gets its own results bucket, so findings are cleanly attributed to the right account. Costs one search per handle.

combined = all handles OR'd into a single row → cheaper (one search), but results land in one shared bucket and attribution is fuzzier. buildKolSearches · config-loader.js:192–210
