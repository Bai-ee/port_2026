Plan: `docs/plans/CONTENT-TRACKS-PROMOTION-MASTER-PLAN.md`. Client: written for `bryan-balli-WUoltG84` (home, @bai_ee), but multi-client since 2026-10-14: tracks are per client (`x_strategy_plans/{clientId}`). Owner decisions D1–D5 + the NAS-staging amendment are binding.

## What it is
- `plan.contentTracks` on `x_strategy_plans/{clientId}` (optional; absent ⇒ defaults, old plans behave exactly as before). Contract: `features/x-strategy/content-tracks.js` (`tracksOf`, `normalizeContentTracks`, `trackForEngine`, `allPromotions`).
- Defaults: **none.** `DEFAULT_TRACKS` is `[]`. Since 2026-10-16 tracks are **one per active Content Center bucket** (see § Bucket tracks); there is no Add track button and the Brain cannot add tracks. A client without a saved plan doc gets no tracks until its first plan save. Every engine belongs to exactly one track; ≤12 tracks, ≤3 benchmarks/track, ≤8 distinct (`PLAN_LIMITS.maxBenchmarkHandles`).
- **Tracks own the profile's benchmark list.** Any plan write (apply / revert / chat plan-change) that changes tracks or pace mirrors `[benchmarkPrimary, ...track benchmarks]` (≤8) into `client_configs.marketingBriefConfig.xGrowth.benchmarkHandles` (`track-profile.js profileBenchmarksFromPlan`, wrapper in `route-handlers.js`). A mirror failure never fails the save (`profileSync.error`). With tracks, the Accounts benchmark list is read-only (derived, links to Plan → Content tracks) and direct profile saves (Handles editor, chat `benchmarks-change`) keep the derived list — only the own handle changes. Old drift: `scripts/x-content/sync-profile-benchmarks.mjs` (dry-run default, `--write`).
- Pace stays `plan.benchmarkPrimary`. Track `share` × authored originals raises per-engine minimums (`track-profile.js applyTrackAllocation`, called from `plan-inputs.js`); never lowers a cap/floor.
- Per-track profile (`track-profile.js`): pools only that track's benchmark corpora. No benchmark ⇒ `status:'no-benchmark'`, fallback own history, surfaced as a gap — never invented numbers.
- Promotions (`promotions.js`): ue → rendered-video packages, record → Discogs, client → client work. URL starts `null`; the link rides **only in the self-reply** (`promotionSelfReply`, `''` when null).

## Daily loop
- Suggestions carry `track`, `promotion`, `package.media {kind,ref}`, `draft.selfReply`; max 5; default library `full`.
- **NAS amendment:** a package with no playable assetRefs ⇒ `package.media = {status:'needs-staging'}`. Save **refuses** (409 `needs-staging`) — never a text-only showcase draft (also enforced for old run docs via the live package). Web + Telegram offer **Stage from NAS** → existing `nas-stage` (owner click = approval; Mac analyzer must be online, UI says so). Never auto-staged. After `STAGE_FOR_PUBLISH` writes `publish-staging/nas/...` onto the package, reads overlay the media (`overlayStagedMedia`) and Save attaches it via `pickMedia`.
- Save writes one unscheduled `social_posts` draft with `mediaStoragePath` = object ref (re-signed at publish), `sourceRef.{track,promotionId}`.
- Cloud cron `GET /api/worker/daily-loop` (`30 11 * * *`): Bearer `CRON_SECRET` (fail closed in prod), `PILOT_CLIENT_IDS` required (503 if unset), **no model drafter**, saved scan only, no bird/X.

## Bucket tracks (2026-10-16)
- Why: tracks were bound only to the 4 fixed engines, so a bucket like `nas` (Throwback Content, whose items carry `engine:'record'`) could not be its own track and the daily loop never read `bucketId`. Each bucket is now its own track.
- Contract (`content-tracks.js`): `buckets: string[]` (ids from `content_buckets/{clientId}/buckets`), each bucket in at most one track, `[]` when absent; ≤12 tracks. Which track an item belongs to: `trackForPackage(tracks, pkg)` = the track listing the item's bucket (`bucketOfPackage`: its `bucketId`, else its engine id, since built-in bucket ids equal engine ids), else the track owning its engine. Used by the daily loop's track tag and strong-match checks (`daily-loop/select.js`; `inputs.js` loads `bucketId`), the digest's "scheduled today" count (`features/email-digest/today-plan.js`) and the strategy agent.
- Sync (`features/x-strategy/bucket-tracks.js`): `bucketTracks(existing, buckets)` is pure; one track per active bucket (bucket order, first 12), label = bucket name, `buckets: [id]`, `engines: [id]` for the built-in `record`/`ue`/`client`/`identity` buckets and `[]` otherwise (e.g. `nas`). An existing bucket track keeps its id and settings; only name and engine are refreshed. A new bucket joins at share 0 (equal shares when every share is 0). A deactivated built-in bucket's engine joins the first track, and promotions always stay with their engine's track.
  - First sync of grouped tracks: each bucket inherits benchmarks, lists, topics and its engine's promotions from the grouped track that held its items (`nas` is found by one item's engine via `readBucketEngine`), and that track's share is split evenly across its buckets. Home 2026-10-16: Design & client work 60% → Video Editing 30% + Graphic Design 30%; Music 20% → Dj Mix Videos 20%; Throwback events 20% → Record Collection Videos 10% + Throwback Content 10%.
  - `syncBucketTracks` runs on every `strategy-get` (Strategy load, MCP, the agent's `get_evaluation`) and after `upsert-bucket`/`delete-bucket` (`quote-targets` route; response carries `tracksSynced`). Only clients with a saved plan doc (version > 0) are synced. It writes through the wrapped plan store (versioned, `by: 'content-center'`, so Revert works, the profile benchmark mirror runs and the Brain's Content Tracks rows are rewritten) and only when the normalized tracks differ; a second run is a no-op. Errors never fail the caller.
- Brain (`brain-sync.cjs` `mergeBrainTracks`): a Re-sync only changes a matching track's share, topics, benchmarks and lists (matched by label, case-insensitive). It never adds, removes or renames a track; an unknown label returns a warning. **Track Targets rows are keyed by track name**, so after the switch they must be re-entered under the bucket names once.
- Strategy agent: `get_tracks` returns `library` per track (item count, top 5 tags, 3 sample titles; `summarizeTrackLibrary` in `route-handlers.js`); `search_inventory` takes an optional `track` (id or name) and every row carries its `track`. The plan-change tool tells the model it may change settings only.
- UI: the Content tracks panel shows the bucket name read-only (`x-strategy-track-<id>-label`; rename the bucket in Content Center), "Content type" chips (`x-strategy-track-<id>-engine-none` when the track has none), no Add track button.
- Not yet (Phase 2): per-track pacing. `postsPerDay` still splits across a track's *engines*, so an engine-less track (Throwback) gets tagged items through the record slots but no posts/day target of its own; bucket `share` caps are still unused. An empty bucket is an empty track (no library suggestions).

## Calendar batch (2026-10-16, Phase A)
- Why: the owner wants any strategy (a track, a bucket, a search, picked items) loaded onto the calendar in bulk as posts to review later; the agent could only propose one post per card, and undated drafts are slotted into the next open times, not on their event date.
- Engine `features/x-content-inventory/calendar-batch.js` (pure plan + an injected writer). Spec = `select` {track (id or name), bucketId, query (every word), ids; AND-combined} + `dateRule` {`anniversary` = next time the item's event month-day (`humanEdits`/`facets.eventMonthDay`, else `eventDate`) comes round, Feb 29 → Feb 28; or `spread` from `startDate` (default tomorrow)} + `perDay` (1–6, default 1; for anniversaries the best item per date wins: owner story, then a full printed date, then a title) + `limit` (≤366). Skips: `already-queued` (an open `social_posts` row for the item), `no-date`, `day-full`, `over-limit`.
- Each item → ONE `social_posts` draft via `ensureDraftPost` (key `calendar-batch:<packageId>`, so a re-run adds nothing): `status:'draft'`, `scheduledAt:null`, `source:'calendar-batch'`, `reviewOn: YYYY-MM-DD` (new additive field in `buildSocialPostRecord`), text = date · title + venue, then the owner's story or `[add your memory]` with `needsStory:true`. The approval gate and the publish sweep refuse the placeholder, so **nothing in a batch can be approved, scheduled or published until the owner writes the memory**.
- Surfaces: route actions `strategy-calendar-batch-preview` (dry run, first 20 rows) and `strategy-calendar-batch-create` (quote-targets route, admin only); agent/MCP tool `propose_calendar_batch` → proposal kind `calendar-batch` (card "Add drafts to the calendar" shows count, date range, skips and 5 samples; the spec is re-planned on Confirm).
- Dates also come from the item's own top-level `eventDate` (birthday packages: `eventDate` = birth date). Text = date · title, where, the item's facts (its story minus the `Source:` line and links), then `[add your memory]`; only an owner-written story (`humanEdits.story`) replaces the placeholder and clears `needsStory`. Drafts carry the item's media (`mediaForItem` = `pickMedia` with the same signer as create-draft-from-item); a media failure never blocks a draft. Home birthdays 2026-10-17 dry run: 14/14 dated, Oct 21 2026 → Sep 5 2027.
- `createStrategyHandlersFromDb` forwards every option it does not consume (`...passThrough`, applied last), so route deps such as `linkItemMedia` / `mediaForItem` reach the handlers. Agent prompt rule: a set of items = ONE `propose_calendar_batch` / ONE `propose_item_media`.
- Home 2026-10-16 dry run (Throwback Content, anniversary, 1/day): 5,434 items, 1,755 dated, **334 drafts Oct 16 2026 → Oct 15 2027**, all needing a memory.
- Phase B (calendar): `month-calendar.js` places every reviewable draft (draft/approved/awaiting) with a `reviewOn` on or after today ON that date, before the undated-proposal pass, so proposals work around it: earliest open time that day (spacing honored), else the end of the window; it is never moved to another day. Rows carry `reviewOn`; `totals.review` / `totals.needsMemory` count them in the month. A past `reviewOn` falls back to the old handling (a needs-story draft goes to `unplaced`). UI: row meta "review day · needs your memory", summary `#x-content-month-summary-review`, and the post sheet tells the owner to replace `[add your memory]`, save, then approve. `updateSocialPost` re-derives `needsStory` for `source:'calendar-batch'` drafts from the text (placeholder in post or self-reply ⇒ true), so saving the memory unblocks approval; approving still schedules nothing (the proposed time becomes real only via Approve & schedule).
- Not yet: an owner button for batches (route actions exist; today it runs through the assistant card), and writing the typed memory back to the library item's story.

## Daily fill (2026-10-17)

`features/x-content-inventory/daily-fill.js` fills the calendar with **review drafts** (`social_posts` status `draft`, `scheduledAt` null, `reviewOn` = the day; source `daily-fill`). Nothing approves, schedules or publishes. Four kinds (post fields `fillKind`, `fillSource {type,id,asOf}`, `expiresAt?`, `bucketId`):

- **baseline**: per track, per day, up to the track's posts/day target (engine targets summed, weekly minimum / 7, same rule as Insights; no engine target = 1/day when `share` > 0, 0 when 0; max 3). Pick order: item whose event date is that day (dated items are only eligible on their own day), then media ready (`mediaState` video/still + `effort` ready), then least recently used. Never an item with an open post (a bare unscheduled draft is *placed* instead), never one picked earlier in the same plan, never one used within 30 days (`lastUsed` from `social_posts`). `EXAMPLE*` / `TODO` seed rows are skipped.
- **quote**: each open, not-dismissed quote target whose 36h window is still open becomes a same-day draft for TODAY only; `expiresAt` = target time + 36h; text = `@handle on this: [add your take]` + the target URL last (statement caption, no question mark); target kept in `sourceRef {kind:'quote-target', url, id, handle}`.
- **narrative**: up to one a day (today, tomorrow) from the Market Signals topics/opportunities, text = `topic: detail` + `Where it shows up in my work: [add your take]`.
- **client-work**: the baseline slots of client-work tracks (engine `client`, or a label like Video Editing / Graphic Design), kind `client-work`, max 1 a day, never added on top of the baseline count.

Gate: `[add your take]` joins `[add your memory]` in `features/social-posting/self-reply.js` (`BLOCKING_PLACEHOLDERS`). **Since 2026-10-17 (PR #25) approval never blocks on them:** every approve path goes through `approveInMemory` (`twitter-service.js`), which strips the placeholder lines (`stripBlockingPlaceholders`, content + self-reply) and clears `needsStory`. Schedule, post-now and the due sweep still refuse text that has either placeholder.

Idempotent: key `daily-fill:<date>:<kind>:<packageId|targetId>` through `ensureDraftPost`; earlier fill drafts on a day/bucket count toward that track's target and a quote/narrative already filled is skipped, so a re-run adds nothing. Rows carry `reason` + `source {type,id,asOf}`.

Wiring: `createStrategyHandlers` deps `readFillContext`, `readQuoteTargets` (plus the existing `readOpenPackageIds`, `readMarketSignals`, `ensureDraft`, `placeDraft`, `mediaForItem`); route actions `strategy-daily-fill-preview` / `strategy-daily-fill-create` (body `{clientId, spec:{from?, days?(1-31, default 7), include?}}`); agent deps `previewDailyFill(spec)` / executor `runDailyFill({clientId, spec, proposalId})`. The cron entry is `runDailyFillForCron(clientId, {today, deps})` (today + 6 days, every kind), with `deps = handlers.dailyFillDeps`.

## One calendar (2026-10-17, PRs #25–#27)

The month calendar is the single review surface for every possible post.
- **Reader:** `features/x-content-inventory/calendar-reader.js` `readUnifiedCalendar` (dashboard handler `handleMonthCalendar` = reader + `withRowThumbs`; a parity test pins them deep-equal). Per day it returns: saved `social_posts` of every status, today's daily-run suggestions, and open quote targets on every day their 36h window covers (rows already saved as posts are de-duplicated). Rows carry `kind`, `approval`, links, window time left and `hasPlaceholder`; totals include suggested + requote counts. Pure row shaping in `month-calendar.js` and `components/dashboard/x-content/calendar-row-model.js`.
- **Approve routes (quote-targets, catalogued tier 1):** `calendar-approve` (post, optional edited content, revision-checked), `calendar-unapprove` (approved + unscheduled → draft), `calendar-suggestion-approve` (suggestion via `saveSuggestionDraft`, or quote via `ensureDraftPost` with the daily-fill key, then approve). Approving never schedules.
- **UI:** `MonthCalendarPanel.jsx` + `CalendarApprovalBits.jsx`: approval marks per row, filter chips All / Unapproved / Approved / Suggestions, inline Approve / Unapprove on rows and in `PostSheet`; quote rows show handle, link, time left. Today card: "Review everything on the calendar".
- **Agent / MCP:** read tool `get_calendar` (from/to/filter; omit both = today + 6 days; result carries `today` + `timezone`); MCP `strategy_get_calendar`. `get_post` / `find_posts` rows carry `approveNote` when text has a placeholder. The prompt gets a `TODAY: <date> (<tz>)` line every turn (`toolDeps.getToday()`, client profile timezone) — the model has no clock and must never guess dates.

## Limits
- Insights → "By content track" renders `evaluation.byTrack` (per-track benchmarks, gaps vs the track lead, "no benchmark yet"); the overall pace section stays labelled separately. Own posts are not tagged by track, so each track's own side is all of your posts (stated in the UI).
- Follow-up: the Content Engine library list is ~6.6 MB (≈1980 NAS + 820 rv rows). Loading `rv-` by bucket needs the shared `inventory-list` loader split (BucketsPanel, two other panels and the day-plan slot lookup all read it) — not done.
- `readInventory()` (un-paginated) reads ids in two bounded queries: the head (READ_LIMIT) and everything after the NAS id range (`NAS_ID_END`), so the NAS archive can't crowd rendered videos out. Sources sorting before `nas-` still share the head budget.
- Corpus refresh needs the owner's Mac: `node scripts/x-content/strategy-refresh-worker.mjs`.
- Library is per client (`clientId`-scoped). The daily-loop cron runs only clients in `PILOT_CLIENT_IDS` that pass `assertClientReady`. Cron copy is plain fallback copy; regenerate with the model from the dashboard.
- Telegram video by URL caps at 20MB (else poster + link). Staging completion is not pushed — reopen Today's posts.
- Strategy-chat edits of `contentTracks` are supported by the proposal schema; no dedicated chat UI.
- Local `npm run build` with the symlinked `node_modules` needs `--webpack` (Turbopack rejects the symlink); Vercel builds normally.
