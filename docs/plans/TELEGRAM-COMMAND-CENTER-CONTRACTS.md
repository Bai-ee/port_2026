## Shared post-service additions (orchestrator, `features/social-posting/twitter-service.js`)
All take `clientId` first, throw `Error` with `.status`/`.code`; `409 revision-conflict` when `expectedRevision` mismatches.
- `claimManualDelivery(clientId, postId, {by, expectedRevision})` → row with `status:'manual'`, `deliveryMode:'manual'`, `manualClaimedAt`, `manualClaimedBy`. Atomic (one transaction). Allowed from `draft|approved|awaiting_approval|scheduled|queued|expired|failed(retryable)`. Refuses `posting` (409 `auto-delivery-started`), `posted` (409 `already-posted`), `needs_review` (409 `needs-review-reconcile`), `rejected` (409 `rejected`). Idempotent on `manual`. Keeps `scheduledAt` as the target time; the sweeper never claims `manual`. A `manual` row still holds its slot/package (counts as pending).
- `recordManualPosted(clientId, postId, {by, permalink, expectedRevision})` → `status:'posted'`, `deliveryMode:'manual'`, `deliveryVerified:false`, `reportedPostedAt`, `reportedBy`, `permalink` (only `https://x.com/<h>/status/<id>` or twitter.com, else null), `reportedPlatformId` (parsed id or null). `twitterId` stays null (never faked). Allowed from `manual` and from the same set as claim (claims atomically in the same transaction). Idempotent on a manual-posted row.
- `releaseManualClaim(clientId, postId, {by, expectedRevision})` → `manual` back to `approved` (if `approvedHash` still matches) else `draft`, `scheduledAt:null`, slot released.
- `approveAndPostNow(clientId, postId, {reviewedBy, expectedRevision})` → approve (same story/placeholder gates) + plan/clearance/reply checks + atomic claim + existing publisher (`postAndRecord` path). Allowed from `draft|approved|scheduled|queued`. Returns `{ok, post, outcome:'posted'|'held'|'failed'|'already-claimed'}`.
- Existing, reused as-is: `getSocialPost`, `readSocialQueue`, `updateSocialPost(clientId, postId, {content}, {expectedRevision})` (revise; voids v2 approval; refuses `manual`), `approveAndSchedule(clientId, postId, {scheduledAt, reviewedBy, expectedRevision})`, `rejectDraft(clientId, postId, {reviewedBy, expectedRevision})`.
- Status display map (all surfaces): `manual` → "Posting manually"; posted+`deliveryMode:'manual'` → "Posted (you reported)"; posted with `twitterId` → "Posted (verified)".

`reviewedBy`/`by` from Telegram = `telegram:<telegramUserId>:<uid>`.

## Telegram storage (track A, `features/telegram/store.js`) — collections
- `telegram_link_challenges/{sha256(code)}` `{uid, clientId, status:'open'|'claimed'|'confirmed'|'expired', expiresAt, telegramUserId, chatId, telegramUsername, firstName, createdAt}`; pointer `telegram_link_pending/{uid}__{clientId}` `{challengeId}`.
- `telegram_bindings/{telegramUserId}` `{telegramUserId, chatId, uid, clientId, status:'active'|'revoked', bindingVersion:int, telegramUsername, linkedAt, revokedAt}`.
- `telegram_updates/{update_id}` inbox `{updateId, receivedAt, status:'received'|'processing'|'done'|'dead', attempts, lease:{workerId, expiresAt}, kind, telegramUserId, payload(sanitized update), error}`.
- `telegram_tickets/{ticketId}` `{clientId, postId, revision, action, params, telegramUserId, bindingVersion, status:'open'|'claimed'|'done'|'superseded'|'expired', expiresAt, claimedAt, result}`.
- `telegram_outbox/{sha1(dedupKey)}` `{clientId, chatId, dedupKey, kind, payload, status:'queued'|'processing'|'sent'|'failed'|'superseded', attempts, nextAttemptAt, lease, messageIds, error, revalidate:{postId, revision}|null}`.
- `telegram_notices/{clientId}__{postId}` `{postId, revision, kind, targetAt, chatId, messageIds, sentAt, state}` (which card is live for a post; used to strip buttons from superseded cards).
- `telegram_settings/{clientId}` `{timezone, leadMinutes, briefingEnabled, briefingHour, quietHours:{enabled,start,end}, notificationsPaused, notifyFailures, notifySuccessSummary, updatedAt}`.
- `telegram_state/{clientId}` `{lastBriefingDate, lastFailureDigestKey}`; `telegram_pending/{telegramUserId}` `{kind:'revise'|'reschedule'|'permalink'|'link-confirm', clientId, postId, revision, ticketId, expiresAt}`.
No composite indexes: query on one field, filter the rest in memory.

## Bot, handoff, scheduler (track C)
`access.js`: `checkBindingAccess(binding, env)` → wraps `requirePilotOwner({clientId: binding.clientId}, {uid: binding.uid}, env)` (from `api/_lib/pilot-access.cjs`) + binding `status==='active'`; returns `{ok, uid, clientId}|{ok:false, reason}`. Every read and every action calls it.
`handoff.js`: `buildHandoffBundle({post, handle, tz, now, mode})→{media:{type:'photo'|'video', url}|null, copyText(exact post.content, sent with NO parse mode), metaHtml (account @handle, local date/time + tz, status label, engine/why, revision), actions:[{action,label}]}`; action sets: unapproved draft → `post-myself, revise, approve-schedule, approve-post-now, reschedule, skip`; approved+scheduled → status reminder `post-myself (take over), reschedule, revise`; `manual` → `posted-it, send-assets, release`; reply rows (`replyTo`) → manual only (`post-myself, posted-it`, plus reply target URL) — never approve buttons; posted/rejected → no actions.
`bot.js`: `createBot(ctx)` with ctx `{db, store, transport, send(outbox-enqueue+drain helper), readModels, briefing, services:{getSocialPost, claimManualDelivery, recordManualPosted, releaseManualClaim, approveAndSchedule, approveAndPostNow, updateSocialPost, rejectDraft}, access, env, now(), botUsername}` → `{handleUpdate(update)}`. Main reply keyboard: What's happening? / Today's posts / Calendar / Upload content / Settings. `/start <code>` → attach challenge, reply "Confirm in HITLOOP to finish linking" (linking completes ONLY in the authenticated web UI). Unbound users get only linking help. Callbacks `t:<ticketId>`: claimTicket → re-read post → ticket.revision === post.revision AND binding.bindingVersion === ticket.bindingVersion AND access ok, else answer "This card is out of date" + send fresh card → apply service → settleTicket → answerCallbackQuery → strip old buttons → send result/new card. Revise: pending `revise` → next text = new copy → `updateSocialPost(...expectedRevision)` → new card. Reschedule: quick picks (+1h, tomorrow same time, next free slot from calendar) + typed `HH:MM` / `YYYY-MM-DD HH:MM` in settings tz → `approveAndSchedule`. Posted-it: optional link reply or "No link". Approve buttons say exactly "Approve & schedule <local time>" / "Approve & post now". Free text without pending state → menu help; never treated as approval. Upload content → T5 hook `ctx.intake?.handleMessage` else "coming next" help. Settings → show + inline toggles (pause notifications, briefing on/off, lead time cycle) + "full settings in HITLOOP".
`scheduler.js`: `runDispatch(ctx,{now})` → `{inbox, handoffs, briefings, failures, outbox}` counts: (1) reprocess reclaimable inbox updates via `bot.handleUpdate`; (2) per active binding (access-checked): handoff notices for posts whose target time (scheduledAt, or calendar `proposed` time for today) is within `[now, now+leadMinutes]` in statuses draft/approved/awaiting_approval/scheduled/queued/manual — dedupKey `handoff:<postId>:<revision>:<targetAt>`; overdue unapproved → "missed, not sent — reschedule?" once per (post,revision); (3) daily briefing at `briefingHour` local once per date; (4) actionable failures (failed/needs_review/expired) once per (post,revision,status); (5) drain outbox: before sending a message with `revalidate`, re-read post — if revision changed or status terminal → `supersedeOutbox`; quiet hours/pause defer `notBefore` for non-urgent kinds (never touch post schedules); 429 → `retryOutbox(retryAfter)`. Latency: cron every 5 min ⇒ handoff arrives ≤ 5 min after entering the lead window.

## Routes (orchestrator)
- `POST /api/telegram/webhook` — secret header check (timing-safe vs `TELEGRAM_WEBHOOK_SECRET`; missing secret ⇒ 503), body ≤ 256 KB, allowed update types `message, callback_query`, `recordUpdate` then ack 200, processing via `after()` + cron reclaim.
- `GET|POST /api/worker/telegram-dispatch` — cron `*/5 * * * *`, `Bearer CRON_SECRET` (fails closed in production).
- `GET|POST /api/dashboard/telegram` — Firebase-auth + `requirePilotOwner`. GET → `{configured, botUsername, binding:{status,telegramUsername,linkedAt}|null, pending:{telegramUsername,firstName}|null, settings}`. POST actions: `link-start`→`{deepLink, expiresAt}`, `link-confirm`→`{binding}`, `unlink`, `save-settings {settings}`.
Env: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` (names only; none set yet). Without the token, transport is not constructed and the dashboard reports `configured:false`.
